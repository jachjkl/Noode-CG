# V9 三次连续优选原理

## 在线候选

两个用户指定的远程源在任务启动时各完整下载一次，不写入仓库缓存。程序随后在线获取 Cloudflare 官方 IPv4 CIDR，并用本次 GitHub `run_id/run_attempt` 派生随机种子，生成恰好 50,000 个唯一官方候选。

`data/previous-official-ips.txt` 是 Actions 在运行后生成的轮换快照：下一轮会排除这些官方样本；同一次任务的新批次还会排除本次已经生成的所有官方 IP 和固定源 IP。

压缩包没有 CIDR 回退文件。官方网页无法读取时，本轮不会拿旧网段假装完成在线刷新。

## 第一层：TCPing 全量轻筛

首轮输入为固定源全量地址加官方 50,000，后续轮次只增加新的官方 50,000。每个唯一 IP 连续进行三次 TCP 连接：

```text
成功数 = 3/3
TCP 平均延迟 <= 200ms
TCP 抖动(总体标准差) <= 200ms
TCP 丢包率 = 0
```

每轮只保留 TCPing 最快的 10,000 个进入昂贵阶段。这样保留全量轻筛，同时避免对数万条明显失败地址执行 TLS、HTTP 和下载。

## 第二层：TLS 与 HTTPS TTFB

候选使用目标 Worker 域名作为 SNI/Host，连续执行三次 TLS 握手和三次 `/cdn-cgi/trace` HTTPS TTFB：

```text
TLS 成功数 = 3/3
HTTPS 成功数 = 3/3
TLS 平均 <= 300ms
TTFB 平均 <= 300ms
TLS 抖动 <= 200ms
TTFB 抖动 <= 200ms
(TCP平均 + TLS平均 + TTFB平均) / 3 <= 300ms
max(TCP平均, TLS平均, TTFB平均) <= 300ms
```

最后一条单项门槛修复了旧规则的漏洞：不能再用两个很快的数值掩盖一个 700ms 以上的慢 TTFB。

HTTPS 响应必须能证明经过 Cloudflare，并返回可识别 `colo`。固定源标签作为端点国家，`colo` 映射作为实际机房国家；任何一方为 `CN` 或未知都淘汰。

严格三项合格结果按 IP 累积到 5,000，不足就追加新的官方批次。

## 第三层：分批下载

合格池不再一次对 5,000 个地址全部下载。程序按质量排序，每次选 1,000 个，并预留日本候选，然后通过候选地址连接 `speed.cloudflare.com`：

- 下载 256KiB；
- 正文完成率至少 95%；
- 下载速度至少 1Mbps；
- 每个地址只进行一次下载。

每批成功结果立即加入累计池。累计达到 500 后进入最终复测；不足时处理下一批 1,000，当前 5,000 用尽后才生成新的官方 50,000。

## 第四层：旧 TOP100 与最终配额

上一轮 TOP100 与本轮下载合格候选合并去重。最终复测包含：

```text
TCPing 三次 → TLS 三次 → HTTPS TTFB 三次 → 下载一次
```

每个地址只进入一个最终复测批次；成功结果持续累积，不会重复测试同一批。最终排序键为丢包率、下载速度、三项平均延迟、最大抖动。

最终发布门槛同时为：

```text
唯一 IP 总数 >= 500
日本端点 >= 15
```

任一门槛未满足都不会覆盖最近一次合格订阅。

## 测速视角限制

GitHub 托管 Runner 的网络位置不能代表中国电信、联通或移动。本项目能保证规则在 GitHub 视角被真实执行，但不能把 Runner 测量转换成不存在的中国三网数据。若以后需要真实三网排序，应添加位于相应网络的自托管 Runner，并把各探针结果合并后再排名。
