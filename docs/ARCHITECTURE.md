# 筛选与测速原理

## 候选池

程序先读取本地 TXT/ZIP 和 `zip.cm.edu.kg/all.txt`。这些地址优先、完整进入候选集合；去重后不足 100,000 个时，再从运行时获取的 Cloudflare 官方 IPv4 CIDR 中按固定种子分散采样补齐。在线源不可用时使用仓库缓存和官方网段快照。

## 验证流程

```text
10 万候选
  → TCP 连接
  → 使用目标域名 SNI 的受信任 TLS
  → /cdn-cgi/trace HTTP 验证
  → 1 MiB 低并发测速
  → 原 V2 加权评分与网段分散
  → TOP 300（合格候选足够时 JP ≥ 10）
```

只有通过目标 Worker 域名 TLS 和 Cloudflare HTTP 验证的地址进入最终排名。评分综合 HTTP/TLS/TCP 延迟、抖动、丢包、速度、地区偏好和协议完整性。

## 测速改进

旧版收到少量正文也会计算速度，连接在下载中途断开时可能得到虚高分。本版请求 1 MiB 测试文件，只有收到至少 95% 正文才写入 `speed_mbps`；否则保留节点但不给速度加分。这样不会因为测速端点偶发超时而把整批可用节点全部删掉。

测速并发限制为 6，减少 GitHub Runner 同时连接过多造成的互相抢带宽。测速候选会先保留最多 30 个 JP 地址，再按 HTTP 延迟填满 600 个测试名额。

## 日本节点保底

最终选择先从已通过 HTTP 的排名中预留 10 个 JP，再按原 V2 国家和 `/24` 网段分散规则填充，最后恢复为总排名顺序。若实际合格 JP 少于 10，程序记录警告并发布正常可用结果，不会为了凑数伪造地址，也不会清空网络。

韩国没有最低数量要求。它与其他未设配额的地区一样按评分自然进入结果。

## 平台访问边界

Cloudflare 优选 IP 只改变用户连接 Cloudflare 的入口。目标网站位于 Worker 出口之后，因此 X、ChatGPT 等平台的可访问性还受 Worker 出口地址、地区限制、风控和 Clash 规则影响。没有真实完整代理链参数时，公开 GitHub Runner 不能替你可靠验证这些平台，也不应上传私人参数来做验证。
