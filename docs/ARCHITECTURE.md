# 筛选与测速原理

## 候选生成

每次运行先全量下载 6 个在线源并读取仓库内的 TXT/ZIP，合并相同的 `IP:端口`，排除环回和私网地址。链接源的全部有效地址都会进入第一轮，不占官方候选名额。

随后从运行时获取的 Cloudflare 官方 IPv4 CIDR 中抽取恰好 50,000 个唯一 IP。Actions 的 `run_id + run_attempt` 形成本次随机种子；`data/previous-official-ips.txt` 保存上次全部官方样本，本次抽样会排除它们。若第一批没有产生 3,000 个合格项，程序继续抽下一批新的 50,000，且本次所有批次互不重复。

## 第一层：形成 3,000 个合格项

```text
全部链接 IP + 官方新 50,000
  → 3 次 TCP：中位延迟、抖动、丢包率
  → 使用目标域名 SNI 的证书验证 TLS
  → 目标域名 /cdn-cgi/trace HTTP 验证
  → 平均延迟 = (TCP + TLS + HTTP) / 3
  → 只保留平均延迟 <= 300ms
  → 不足 3,000 则追加另一批官方 50,000
```

只有三项延迟都存在且目标域名返回有效 Cloudflare trace 的地址才能进入 3,000 名单。300ms 边界是包含关系：等于 300ms 可进入，高于 300ms 被排除。

## 第二层：本轮 TOP300

平均延迟最好的 3,000 个地址全部下载 1MiB 测试文件。只有收到至少 95% 正文才记录速度，避免把中途断流误判成高速。随后严格按以下元组排序：

```text
(丢包率升序, 下载速度降序, 平均延迟升序)
```

速度测试未完成的地址不会进入本轮 TOP300。

## 第三层：旧 TOP100 与本轮 TOP300 复测

程序在覆盖输出前读取上一轮 `output/nodes.json` 的前 100，并保存到 `data/previous-top100.json`。本轮 TOP300 与旧 TOP100 合并去重后，旧成绩全部清空，再执行：

```text
10 次 TCP → TLS → HTTP → 平均延迟 <= 300ms → 完整 1MiB 下载
```

最终仍按“丢包率、下载速度、平均延迟”选 300。旧地址只有在本轮重新通过测试时才能留下。若最终不足 300，`preserve_last_good` 会阻止空列表或不完整列表覆盖旧订阅。

## 网络基线与平台访问

运行开始时会直接测量 GitHub Runner 到 Google、Cloudflare 和 GitHub 的整体延迟，写入 `output/health.json`。这用于识别 Runner 本身的网络异常，不参与单个候选排名。

一个公开入口 `IP:端口` 并不包含 UUID、Worker 路径和完整代理链，因此无法在 GitHub 上针对每个候选可靠测试 X、YouTube、Telegram 或 ChatGPT。最终平台可用性还受 Worker 出口、地区限制、风控和 Clash 规则影响。
